Building an IT service desk three times

How the department’s ticketing grew from a Power App into a custom web app, and why each version replaced the last.

RoleUsersStack (v3)Status
Designer and developer, all three versions 5 IT technicians, about 100 staff React on Azure Static Web Apps, Microsoft sign-in, Azure SQL, Blob storage v2 in use; v3 in staff testing, launching January 1, 2027

The problem

The IT department was paying for an outside help desk service. It was expensive for what we used, and it wasn't built around how a small IT team supporting about 100 staff actually works. We wanted something more affordable that fit our needs exactly.

Three versions

  1. v1 · 2023

    Power Apps: the bare minimum

    A simple Power Platform app to get every request into one place we owned. It was rough, but it proved we didn't need the paid service.

  2. v2 · 2024

    Power Apps: one place for everything

    Brought access requests and equipment rentals into the same system as tickets, so staff had one place to ask IT for anything. This is the version in use today.

  3. v3 · 2025–26

    React on Azure: built to grow

    v2 ran into SharePoint's row limits, and Power Apps had become slow. v3 is a React app on Azure Static Web Apps with Microsoft sign-in, an Azure SQL database, and Blob storage for files. IT staff are testing it now, and it goes live January 1, 2027.

What it does

  • Help desk tickets for 5 technicians and about 100 staff
  • Access requests
  • Equipment rentals and inventory management, internal and external
  • Event calendars
  • Email notifications and updates

What I did

  • Designed and built all three versions, from the data model to the screens staff use.
  • Chose to move off SharePoint and Power Apps when they hit their limits, and rebuilt on a stack that can grow: React, Azure SQL, and Blob storage, with the same Microsoft sign-in staff already use.
  • Manage v3 in GitHub, so changes are versioned, reviewed, and deployed automatically.

Results

  • Replaced a paid outside service with a system the department owns.
  • Tickets, access requests, equipment, and events now live in one place instead of several.
  • I've handled about 1,640 tickets myself, roughly a third of the department's total.

What I learned

Low-code tools are the right way to start: they get a working system in front of people fast and prove the idea. Once the requirements settle and the platform starts fighting you, owning the code gives you control over performance, features, and how changes ship.
